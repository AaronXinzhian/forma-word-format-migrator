# Forma 赋式｜智能文档格式引擎

> 一份范本，万卷同式。

Forma 赋式把一个 Word 文档的标题、正文、标题多级编号、表格、主题和页面设置保存成可复用的“格式方案”，以后可以直接套用到其他 Word 文档，不必反复选择原格式源。项目同时提供 Mac 与 Windows 桌面版，两端使用相同的 `.wfstyle` 格式方案。

## 可用版本

- **Mac 版**：macOS 13 或更高版本，支持 Apple Silicon 与 Intel Mac。发布包已经内置固定版本的 Universal Python 与 `lxml`，普通用户不需要安装 Python、开发工具或其他解析组件。
- **Windows 版**：Windows 10 或 Windows 11 x64；Windows 11 ARM64 可通过系统的 x64 兼容层运行。便携包已经包含 .NET、Python 和 `lxml`，普通用户不需要安装开发环境。请先完整解压 ZIP，再运行 `FormaFushi.exe`。

## 三步使用

1. Mac 双击 `Forma 赋式.app`；Windows 完整解压便携包后双击 `FormaFushi.exe`。选择一个 `.docx`、`.docm`、`.dotx` 或 `.dotm` 作为格式来源。
2. 程序分析文档，展示其中**实际使用过**的段落样式、字符样式和表格样式；如果标题只实际使用到三级，还会按前三层的设计逻辑智能补全标题四、标题五。确认后，这套格式会保存到“我的格式库”；也可以在 Mac 版中打开“编辑格式方案”，调整标题与正文的字体、字号、粗体、颜色、段落对齐、间距、行距和缩进，以及表格底色与首行强调色。
3. 选择需要修改格式的 `.docx` 或 `.docm`，先查看真实目标预检（段落、标题、表格、字体及页面处理），再指定新文件保存位置。Mac 版只有预检有效时才能生成；模板、目标或选项变化后需重新预检。

程序始终生成新文件，不会改写格式源或目标原文件。格式源在导入后可以移动或删除，已保存的格式方案仍可使用。

在“我的格式库”中，每套格式右侧都有独立的删除按钮。确认后程序只会把对应的 `.wfstyle` 格式方案移到 macOS 废纸篓或 Windows 回收站，不会删除原来的样板 Word 文件、目标文件或已经生成的文档；误删时可以恢复。

## 格式预览里会看到什么

- 样式名称、类型和在源文档中的使用次数。
- 字体、字号、粗体、斜体、颜色、段前段后、行距、标题级别和标题编号规则等有效属性。
- 标题在源文档中实际使用的段落缩进；编号列表自身的定位数据不会被误当成标题的 Left 值。
- 表格样式的主要填充色和强调色。
- 纸张大小、方向和页边距。
- 文档中检测到的手工直接格式数量。
- 由标题一至标题三推导出的标题四、标题五会单独标记为“智能补全”，使用次数为 0，不会冒充源文档真实使用过的格式。

普通未使用样式不会出现在预览列表中。为了保证 Word 的继承关系、主题和编号仍然有效，程序会在内部保留必要的格式依赖，但不会把它们混进用户要选择的列表。

## 在程序中修改格式方案

Mac 版可以在读取模板后直接编辑格式方案。编辑器一次可以调整多个实际使用样式，并实时显示样式示意：

- 标题、正文和字符样式：中文字体、西文字体、字号、粗体和文字颜色。
- 字体选择器：可搜索整份模板中实际使用的字体、macOS 已安装字体、本地化名称和 PostScript 名，并标明“已安装”“别名匹配”“本机未注册”或“匹配冲突”。模板原字体始终保留在列表中，即使它没有安装在当前 Mac 上。
- 段落样式：对齐方式、段前/段后、单倍/最小值/固定值行距，以及按字符或磅设置的左右缩进、首行缩进和悬挂缩进；输入 `2 字符` 会保存为 Word 的真实字符缩进，不会在文本前插入空格。
- 表格样式：表格基础底色、首行强调色、边框样式/颜色/宽度与上下左右单元格边距。
- 标题编号：在已有编号规则上调整数字形式、层级标点模式、起始值和随上一级重启；只允许当前及上级占位符，不凭空生成缺失的编号体系。
- 编号标题：修改标题字体后，对应序号标签会同步更新，避免标题文字与数字使用不同字体。

如果模板没有实际使用表格，编辑器会额外显示一项“可选表格方案”。只有修改并保存这项方案后，它才会用于目标文档；保持不动时，程序仍保留目标表格原来的视觉样式，仅清理单元格里错误的两字符首行缩进。旧版同格式库也会在内存中获得这项编辑能力，不需要重新导入模板，原 `.wfstyle` 文件不会被悄悄改写。

保存时始终派生一个新的 `.wfstyle` 文件，原格式方案不会被覆盖。派生方案会获得新的 ID、完整性校验和与格式指纹；如果不满意，可以删除新方案或继续使用原方案。编辑器修改的是可复用格式资产，不会反向改写原模板 Word 文档，也不会读取或保存模板正文。

Mac 编辑器的“重置全部”需确认，并可撤销；切换字符/磅单位会清除旧单位覆盖值并明确提示，不把 2 字符误解释成 2 磅。格式库支持导入和导出 `.wfstyle`：先校验内容，重复规则复用已有方案，同 ID 不同规则拒绝覆盖。损坏方案会显示原因并提供 Finder 定位，不会静默丢失。

字体预览会分别使用中文与西文字体。如果模板使用 Aptos、Calibri、Cambria 等可能仅由 Microsoft Word 提供、而未在 macOS 全局注册的字体，Forma 仍会原样保存 Word 字体名；只是程序内的示意预览会明确回退到系统字体。程序不会把 SimSun 等未安装字体擅自替换成 Songti SC 或其他外观相似的字体；最终呈现以打开生成文档的 Word 可用字体为准。

## 标题四、标题五如何智能补全

只有当格式源实际、连续使用了标题一、标题二、标题三，而没有实际使用标题四或标题五时，程序才会补全缺少的层级。源文件中仅仅“定义过但没用过”的标题四、标题五会被视为无效默认值，不参与推导。

补全规则会延续前三层真实呈现出的字体、颜色、粗体/斜体、字号变化、段前段后、行距和对齐，并设置正确的大纲级别。字号会继续沿用最近的层级变化，同时以正文字号为下限，避免越推越小。如果前三层构成可重复的多级编号，即使 Word 把一级与二、三级保存到了不同编号实例中，程序也会逐层保留原序号的字体、标点、缩进和对齐，并合成为同一套五级计数，延伸为“1.1.1.1”和“1.1.1.1.1”。一、二级序号共同指定的字体会继续用于智能补全层级的数字，字号等层级属性仍跟随各自标题，不会盲目复制三级序号的特殊设置；已保存的旧格式库也会在应用时自动校准。源格式没有编号时不会新增编号，编号文字含有无法可靠推导的“章、节、款”等语义单位时也不会擅自编造。

## 本机会保存什么

格式方案保存在：

```text
# macOS
~/Library/Application Support/FormaFushi/style-packs/

# Windows
%LOCALAPPDATA%\FormaFushi\style-packs\
```

每个 `.wfstyle` 文件只包含经过白名单处理的格式 XML 和预览索引：样式、主题颜色、字体名与别名映射、编号规则、部分格式设置与页面布局。它不会保存源文档正文、页眉页脚文字、批注、图片、宏、嵌入对象或字体文件；预览中的文字是程序生成的示例，不是源文档摘录。

Mac 首次升级会安全迁移旧 `WordFormatMigrator` 目录；新旧目录同时存在时不覆盖，迁移失败时继续读取旧位置。加载外来格式包也会校验格式部件、关系类型、命名空间和内容钩子，拒绝正文、二进制及外部关系，即使其校验和正确。

首次读取时，格式方案显示名称默认取源文件名；派生新方案时可以修改名称。磁盘文件名使用随机 ID，避免把敏感文档标题暴露在 Finder、备份或诊断路径中。自定义样式名称本身属于 Word 格式信息，会被保留。

## 应用到目标文档时

会替换：

- Word 样式系统，包括标题 1/2/3、正文、自定义样式和表格样式。
- 主题颜色、主题字体、字体表和编号定义。
- 格式源实际使用的标题多级编号，例如“1”“1.1”“1.1.1”。如果目标标题文字开头已有与最终层级计数一致的手工序号，例如“第三章”“3.1”“3.1.1”，程序会只清理这段重复前缀，再使用自动编号；标题正文保持不变。
- 标题段落会采用格式源实际使用的 Left、首行和悬挂设置。编号定义中的制表位与定位数据仍会保留，但不会再把三级编号的 `0.49"` 等值错误显示成标题段落 Left。
- 如果目标文件从“第三章”等非 1 章节开始，程序会保留起始章号，使后续自动编号继续显示为“3”“3.1”“3.1.1”。
- 如果格式源只实际使用标题一至标题三：采用智能补全的标题四、标题五；目标原先随意设置的四、五级标题直接格式会被清理。
- 目标文字上的手工字体、字号、粗体、颜色、底纹等直接格式。
- 目标段落上的手工对齐、缩进、间距、边框和编号等直接格式；格式源没有实际表格样式时，表格单元格段落采用下面的保留规则。
- 如果格式源实际使用了表格样式：清除目标表格的直接边框、底纹和边距，并采用格式源实际使用的表格样式；普通单元格段落仍会防止继承正文样式中的“两字符首行缩进”。
- 默认情况下采用格式方案的纸张、方向、页边距、分栏和页面边框；也可关闭此选项。
- 可选“所有标题向下调整一级”：正文中的标题一变标题二、标题二变标题三，依次到标题八变标题九，样式、自动编号和缩进会同步切换；标题九受 Word 的九级上限保持不变。格式库只有前三层时，程序会按同一设计逻辑在本次应用中继续补全所需的标题六至标题九。

会保留：

- 目标文档的文字、图片、表格结构、超链接、批注、脚注、尾注和嵌入对象。
- 普通正文、表格和页眉中的项目符号与自动编号，包括独立编号序列、中途重启和图片项目符号；即使目标与模板恰好使用相同的内部编号 ID，也会隔离后再保留其列表语义。新增的标题层级和隔离导入的正文列表会同时分配独立列表身份，避免 Word 合并旧定义后不显示标题四、标题五的序号。
- 目标文档的页眉页脚内容和关联关系。
- 表格列宽、合并单元格、重复标题行等结构信息。
- 如果格式源没有实际使用过表格样式：保留目标表格原来的样式、边框、底纹、列宽、边距、合并关系、单元格属性，以及单元格段落原有的对齐、间距、编号和左右缩进；仅把明确的“两字符首行缩进”改成零。对于 Word 只在段落上留下 `firstLine=240` 等磅值、同时又从正文样式继承“两字符”的情况，也会把两种单位一起归零，避免表格文字仍然空出两个字符。
- 对需要清理的普通表格文字，程序会同时应用隐藏的“表格正文（无首行缩进）”样式，并保留段落上的零值覆盖。这样在 Word 中新增行、增加单元格段落、粘贴内容或清除直接格式后，也不会再次从正文样式继承两字符缩进；正文段落本身的两字符首行缩进不受影响。带自动编号、悬挂缩进或大纲级别的表格段落仍会保护其列表结构，除非段落本身明确保存了“两字符”首行缩进。
- 上下标、公式标记、语言、从右到左书写和隐藏文字等带有内容语义的属性。
- `.docm` 目标文件中的宏；生成文件仍必须使用 `.docm`。

目标中找不到对应源样式的段落，会按同级标题、同名样式或正文样式进行匹配。

## 需要注意

- 源文档里的手工直接格式不是可复用的 Word 样式，程序会提示数量，但不会把每一处手工改动保存成独立样式。表格上手工画出的边框和底纹也不等于“表格样式”；如果希望复用这套表格外观，请先在 Word 中把它保存为表格样式。建议重要格式先定义为“标题 1”“标题 2”“正文”或自定义样式。
- 标题段落上实际使用的对齐、间距、行距和缩进会安全汇总后保存；标题文字开头手工输入的全角空格或普通空格属于正文内容，不会被当成段落格式复制。需要“空两格”效果时，应使用编辑器中的“首行缩进 2 字符”。
- 推荐在 Word 中使用“多级列表/自动编号”。对于目标标题开头已有的手工序号，程序只在标题级别、数字分量、父子路径和预计计数全部一致时清理；正文中的数字、版本号、日期以及无法可靠判断的前缀不会被删除。
- 目标中的四、五级标题需要已经标记为 Word 的“标题 4”“标题 5”或对应大纲级别。仅靠手工加粗、放大字号的普通正文无法可靠判断它究竟是四级还是五级标题，程序不会凭外观猜测语义。
- 旧版格式库应用时仍会自动修复兼容但分散的多级编号，并补齐智能生成标题遗漏的序号字体；但旧文件没有保存标题段落实际使用过的缩进，程序不会冒险猜测。请用 2.4.0 或更高版本重新导入一次格式源，即可永久保存每级标题的 Left、首行与悬挂细节，并在预览中看到“智能补全”的标题四、标题五及其编号卡片。
- “所有标题向下调整一级”是一次结构操作，默认关闭。若把已经处理过的结果再次作为目标并重新勾选，标题会再次下调一级；标题九仍保持标题九。
- 从旧版本保存的格式库仍可使用；如果标题编号原来是直接应用在标题段落上的，建议用本版本重新导入一次格式源，以完整保存编号层级。
- 老式 `.doc`、加密或密码保护文件需要先在 Word 中转换或解锁。
- 图片自身、图表、SmartArt 和嵌入对象内部的视觉设计不会被重绘。
- 生成后建议用 Word 打开新文件，更新目录、交叉引用和域，并快速检查分页。
- 内部测试构建如果尚未完成 Apple 公证，macOS 可能提示来源不明；正式外部分发应使用 Developer ID、Hardened Runtime 与 Apple 公证重新构建。Windows 便携版暂未使用商业代码签名证书，首次启动前请核对发布包 SHA-256；如 SmartScreen 拦截，确认来源后选择“更多信息”→“仍要运行”。

## 命令行方式（可选）

应用中包含 `style_pack_manager.py` 和 `word_style_transfer.py`。高级用户也可以运行：

```bash
python3 style_pack_manager.py create-pack \
  --source 格式源.docx \
  --out 我的格式.wfstyle \
  --name 我的格式

python3 style_pack_manager.py apply-pack \
  --pack 我的格式.wfstyle \
  --target 内容目标.docx \
  --out 内容目标-格式已替换.docx
```

如果应用格式时希望保留目标文件原来的纸张和页边距，可追加 `--preserve-page-layout`；如需把正文中的所有标题向下调整一级，可追加 `--demote-headings`。

## 开发与验证

运行全部文档处理回归测试：

```bash
python3 -m venv build/forma-tests-venv
build/forma-tests-venv/bin/python -m pip install -r requirements-dev.txt
build/forma-tests-venv/bin/python scripts/gen_ui_strings.py --check
build/forma-tests-venv/bin/python -m unittest discover -s tests -p 'test_*.py' -v
python3 scripts/check_project_docs.py --sync
```

仅运行已安装开发依赖环境中的回归测试也可使用：

```bash
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

在 Mac 上构建同时支持 Apple Silicon 与 Intel 的签名应用和压缩包：

```bash
FORMA_BUILD_PYTHON="$PWD/build/forma-tests-venv/bin/python" ./scripts/build_macos_app.sh
```

Mac 构建默认使用已验证的 SDK 26.5（可用 `FORMA_MACOS_SDK` 明确指定其他 SDK 并自行验收），先运行全部 Python 与 Swift 测试，再校验固定哈希的 Universal Python/lxml、执行双架构运行时和真实迁移 smoke，最后检查解压后的签名及运行路径，生成 ZIP、SHA-256 和源码来源清单。日常开发构建可以使用本机临时签名；正式发布需干净已提交源码并设置：

```bash
MACOS_SIGNING_IDENTITY="Developer ID Application: …" \
MACOS_NOTARY_PROFILE="forma-notary" \
FORMA_REQUIRE_NOTARIZATION=1 \
./scripts/build_macos_app.sh
```

未设置 Apple 公证凭据时，输出文件名会带 `-local-adhoc` 或 `-local-unnotarized`，不会覆盖同版本的正式发布包；只有完成 Developer ID 签名与 Apple 公证的构建才使用正式文件名。

应用外壳、用户界面、格式编辑器、任务状态、取消和结果报告使用 Swift/SwiftUI。当前复杂 OOXML 迁移内核作为应用内私有组件随包发布，用户不会感知或安装其运行环境；后续模块会在同一真实文档回归集保护下逐步迁移到 Swift。

在 Apple Silicon Mac 上交叉构建自包含的 Windows x64 便携包：

```bash
./scripts/build_windows_app.sh
```

交叉构建校验固定版本 .NET、Windows Embeddable Python 与 `lxml`，包名明确标记 `-local-crossbuild`；不能验证 Windows Python、SmartScreen 或实际 GUI。在 Windows PowerShell 7 中使用 `./scripts/build_windows_app.ps1` 执行本机发布、包内 Python、真实迁移和解压后重复 smoke。正式分发另需 `-RequireSigning`、签名证书及时间戳服务。CI 的 Windows 任务执行此原生门禁，但不自动创建 GitHub Release。

构建结果写入本机 `build/` 和输出目录，不提交到 Git。源码来源清单记录提交、dirty 状态、实际工具链和逐文件 SHA-256，拒绝未解决合并；构建首尾输入必须一致。Mac 保留原有 bundle ID，两个平台继续使用相同 `.wfstyle` 结构。
